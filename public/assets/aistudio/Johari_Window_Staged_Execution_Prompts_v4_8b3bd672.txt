STAGE 3A — SESSION CREATION, SELF-ASSESSMENT, AND ATOMIC OPEN/INVITATION ISSUANCE
============================================================

PROMPT:

Execute Stage 3A only. Re-read Phase A, Phase B, the invitation-issuance section of Phase C, and the related database/security rules in the master specification.

1. Implement authenticated owner session creation with server-side limits: expected participants 1–50, maximum 20 non-finalized sessions per owner by default, enforced transactionally under concurrent requests. Persist all Phase A settings. When `expected_participants` is below five and low-sample opt-in is off, warn that finalization will require at least five responses and offer the explicit opt-in with its acknowledgement. The owner RPC must reject enabling the flag unless the acknowledgement is affirmatively supplied in the same request.
2. New sessions must start in `draft`. Do not create or return invitation tokens during session creation.
3. Implement the database-backed 55-adjective self-assessment selector with 5–7 selections, deduplication, live counter, server validation, and submission confirmation.
4. Make the self-assessment immutable once the session opens.
5. On self-assessment submission, atomically save the self-assessment, generate the initial invitation batch equal to `expected_participants`, insert only token hashes, and transition draft → open. If any step fails, none of the transition may commit.
6. Generate each token server-side using 32 cryptographically secure random bytes, encode as base64url without padding, and store only its SHA-256 digest. Use the owner's JWT for the owner-authenticated RPC; it must verify `auth.uid()` and ownership. Keep plaintext tokens only in Edge Function memory and return each exactly once in the successful response.
7. Return complete `/invite#<token>` URLs to the owner after the atomic open transition. Set `Referrer-Policy: no-referrer` and `Cache-Control: no-store`; do not load third-party analytics/scripts on invitation pages. Never log/store plaintext tokens or put them in URL paths or query strings.

STAGE 3A ACCEPTANCE:
- Owner can create an authenticated draft session.
- Self-assessment uses the canonical database bank and enforces exactly 5–7 distinct adjectives.
- Self-assessment submission atomically opens the session and issues the initial invitation batch.
- Session creation itself issues no invitations.
- Tokens are 256-bit, stored only as SHA-256 digests, and returned plaintext once.
- Self-assessment cannot be edited after the session opens.
- A target below five produces the required create-form warning and explicit opt-in offer.
- Concurrent session creation cannot exceed the per-owner cap.

STAGE 3B — INVITATION ENTRY, READ-ONLY VALIDATION, AND PARTICIPANT SUBMISSION
============================================================

PROMPT:

Execute Stage 3B only. Re-read the participant workflow and token/security rules in the master specification. Assume Stage 3A has completed and has been verified.

10. Implement `/invite` token extraction from the URL fragment and `/join` accepting only a complete invitation URL or the complete raw 256-bit token. Do not support short numeric or alphanumeric codes.
11. Implement read-only token validation through an HTTPS POST body. Hash the token server-side with SHA-256. GET, link preview, validation, and page refresh must never consume an invitation. Keep the fragment until successful submission; remove it only after success. Do not store tokens in localStorage, sessionStorage, IndexedDB, or cookies.
12. Implement participant submission through a server-side Edge Function and atomic participant RPC. The Edge Function validates payload shape; the database transaction rechecks token digest, invitation/session state, database-time session expiry, 5–7 valid distinct adjective IDs, and name-collection rules; it inserts participant/responses and consumes the invitation in one transaction. Participant RPCs using the service/secret key must not depend on `auth.uid()`.
13. Use row locks and a consistent lock order. Two concurrent submissions using the same invitation must result in exactly one success. Different valid invitation tokens must be able to submit concurrently without corrupting data.
14. Apply configurable rate limits to validation and submission. Bucket keys must be HMAC-SHA-256 of the request IP and/or token digest using a server-only secret, with a short TTL. Never store raw IPs, raw tokens, or plain unsalted hashes of IP addresses.
15. Never claim that individual links prove distinct real-world people. The app guarantees single use per token only unless separately verified identity is implemented and tested.

STAGE 3B ACCEPTANCE:

- Participant submissions persist atomically and each invitation can succeed once only.
- Participant names are requested/stored only when enabled.
- Session expiry uses database time and cannot be bypassed by changing a client clock.
- Multi-connection or parallel HTTP tests prove same-token single-success behavior and safe different-token concurrency.

STAGE 6 — JOHARI CALCULATION ENGINE AND FREQUENCY TESTS
============================================================

PROMPT:

Execute Stage 6 only. Re-read the mathematics, test vector, adjective bank, and authoritative database calculation requirements in the master specification.

3. Calculate Open = S ∩ P; Blind = P − S; Hidden = S − P; Unknown = U − (S ∪ P) in PostgreSQL. Mirror the same calculation in TypeScript only for reference/parity tests and optional UI-side checks.
4. Compute frequency for every adjective as the number of distinct submitted participants who selected it. Frequency must not affect quadrant membership.
5. Assert that each quadrant is pairwise disjoint and their union is exactly U. Every adjective must appear exactly once.

The database integration-test session must set `allow_small_sample_results = true` and include the explicit test-fixture acknowledgement because the vector contains only two feedback participants. Assert that both implementations return identical quadrant assignments and frequencies. Then run the same test with the production threshold disabled and verify finalization is rejected for fewer than five participants.
   - Subject: Able, Caring, Clever, Happy, Kind.
   - Participant 1: Able, Caring, Brave, Friendly, Happy.
   - Participant 2: Clever, Kind, Brave, Calm, Friendly.
