PHASE C — INVITATION

Invitation issuance timing is strict:
- Do not generate invitations during session creation.
- When the subject submits the self-assessment, the server generates the initial number of invitations equal to `expected_participants` and atomically saves the self-assessment, inserts only token hashes, and changes the session from `draft` to `open`.
- The owner receives each plaintext token exactly once in the successful response and sees/copies each complete invitation URL. Generate the raw tokens and SHA-256 hashes inside the server-side Edge Function; call an owner-authenticated RPC using the owner's JWT and pass only the hashes plus self-assessment IDs. That RPC must verify auth.uid()/ownership and atomically insert the self-assessment, insert the full initial batch of hashes, and transition the session to open. Return invitation IDs from the RPC, then pair those IDs with the raw tokens held only in Edge Function memory for the one-time owner response.
- If the transaction commits but the response is lost, the original plaintext tokens cannot be recovered. The owner must use reissue: revoke an unused invitation and mint a replacement. Also provide a bulk recovery action to revoke and reissue all currently issued-but-unused invitations after a lost batch response. Make single and bulk recovery obvious and safe.
- An unused invitation may be revoked and replaced. A used invitation cannot be reissued.
- The owner may issue additional invitations while the session is open, while fewer than 50 invitations are active and the 200-record lifetime token-issuance cap has not been reached.

Each invitation uses at least 256 bits of cryptographically secure randomness (32 random bytes, encoded as base64url without padding). Generate tokens only server-side. Calculate a SHA-256 digest of each token and store only the digest (for example, lowercase 64-character hex or bytea). SHA-256 is appropriate because tokens have high entropy and must support indexed exact lookup; do not use bcrypt/Argon2 password hashing for these random lookup tokens.

Invitation URL format is `/invite#<token>`. Never put tokens in URL paths or query strings. Set `Referrer-Policy: no-referrer` and `Cache-Control: no-store` on invitation pages/responses. Do not load third-party analytics, advertising, or external scripts on invitation pages. Never log raw tokens or token hashes.

A link preview, initial GET, page refresh, or validation/preview request must NOT consume an invitation. Only a valid participant submission consumes it, in the same atomic database transaction that stores the response. `sessions.expires_at` is the only expiry field; do not add `participant_invites.expires_at`. Every invitation validation/submission checks the parent session expiry using database time.

Provide:
- One complete URL per invitation.
- Copy-link action for each newly issued URL.
- Native share action where supported.
- Clear status for each invitation: issued, submitted, or revoked. Derive “expired” from expiry timestamps and “replaced” from revocation/replacement history; do not add inconsistent stored states unless the implementation has a documented need.
- A recover/reissue action for one unused invitation that revokes the previous token and returns a newly generated token once.
- A bulk recovery action that revokes and reissues all currently issued-but-unused invitations and returns the new URLs once.
- A generate-additional-invitation action.
- A note that a one-time link prevents reuse of that link, but does not prove that separate links belong to separate real-world people.

If browser reload or network failure loses a plaintext link, never attempt to reconstruct it from the hash. Use the revoke-and-reissue flow.

OPEN AREA = S ∩ P
BLIND AREA = P − S
HIDDEN AREA = S − P
UNKNOWN AREA = U − (S ∪ P)

SECURITY IMPLEMENTATION RULES — REQUIRED

1. Owner authentication: Supabase Auth is required. Default to email magic link/email OTP. Every owner operation must verify the caller's user JWT and session ownership in a server-side Edge Function or owner-scoped database function.
2. Owner JWT versus privileged server calls must be separated:
   - Owner-facing Edge Functions must validate the user's JWT and use a user-scoped Supabase client carrying that JWT when invoking owner RPCs. The database function must check `auth.uid()` and `sessions.owner_id`.
   - Participant-token Edge Functions may use the server-only Supabase secret/service-role key for narrowly scoped privileged database work. These calls do not represent a logged-in owner; `auth.uid()` may be null. Participant-only RPCs invoked with the secret/service-role credential must NOT rely on `auth.uid()`. They must validate the SHA-256 invitation digest, invitation state, session state, expiry, and all submitted data inside the transaction.
   - Do not mix the two call paths or write one RPC that assumes `auth.uid()` is populated for both.
3. Enable RLS on every API-exposed table. Default to deny. Revoke default broad grants. Grant only the minimum operations needed. Sensitive tables should preferably live in a non-exposed schema.
4. Browser clients must never select invitation token hashes, raw participant rows, self-assessment response rows, raw adjective responses, or session result snapshots directly. Return safe DTOs through authorized Edge Functions/RPCs.
5. Participant validation endpoint: accept token only in a POST body, hash it using SHA-256 server-side, perform read-only validation, and return only subject name/title plus minimum form metadata. It must not consume the token.
6. Participant submission endpoint: require HTTPS POST. Call a narrowly permissioned participant RPC using the server-only secret/service-role credential. The RPC must recheck the token digest, lock rows in a consistent order, verify invitation/session status and database-time expiry, validate adjective IDs and exactly 5–7 distinct selections, enforce participant-name rules, insert participant and responses, and mark the invitation submitted in one transaction. Exactly one of concurrent submissions using the same invite may succeed.
7. Owner RPCs: use the caller's authenticated JWT, verify `auth.uid()` is not null, verify ownership inside the function, and never accept owner_id from untrusted client input as proof of ownership.
8. SECURITY DEFINER: use only when necessary. Prefer SECURITY INVOKER. Every SECURITY DEFINER function must set `search_path = ''`, fully qualify all relation/function references, validate the caller/credential explicitly, revoke EXECUTE from PUBLIC/anon by default, and grant EXECUTE only to the intended role. Place privileged functions in a non-exposed schema where practical.
9. Invitation token generation: use a cryptographically secure generator for 32 random bytes. Store only SHA-256 digest. Return plaintext only once to the owner at issuance/reissue. No plaintext token in logs, analytics, database, error telemetry, URL path/query, or browser persistent storage.
10. Link safety: invitation token is in the URL fragment only. Set `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. Do not load third-party scripts on invite routes. Link preview/GET/validation must not consume an invitation. Consume only in successful atomic submission.
11. Realtime: use private Broadcast, not raw Postgres Changes, for dashboard progress. Authorization on `realtime.messages` must permit only the owning authenticated user to receive their session topic. Broadcast only progress counts/status. Never include names, invite IDs, token hashes, adjective IDs, frequency counts, or raw response rows. Configure private channels (`private: true`) and disable public channel access for the project when feasible. If a correct private Broadcast policy cannot be proven, use owner-authenticated polling instead.
12. Rate limiting: protect invitation validation and submission endpoints. Prefer platform/gateway throttling plus short-lived server-side counters. Derive each bucket key as HMAC-SHA-256 of the request IP and/or invitation token digest using a server-only secret that is never sent to the browser. Never use a plain unsalted hash of an IP address, and never persist raw IPs or raw tokens. Give counters a short TTL, make limits configurable, and test throttling plus legitimate shared-network behavior.
13. Results: block until finalized. Only the authenticated owner may access results. Participants cannot read session_results. No public results route or public sharing link in this version.
14. Expiry: use database `now()` in all validation/submission/finalization decisions. Expiry blocks participants only; it does not prevent the owner from viewing the dashboard or finalizing valid collected responses.
15. Session deletion: implement hard delete with cascading foreign keys or a verified transaction. Do not merely set a deleted flag. Prove deletion with a privileged integration test.
16. Privacy: explain that `collect_participant_names = false` means the app does not ask for or store participant names; it does not guarantee anonymity against social inference or link-distribution knowledge. Individual responses remain private. Do not imply that five participants mathematically guarantees anonymity.
17. Test RLS and authorization with at least two separate owner accounts, a signed-out client, and participant token clients. A successful UI test is not proof that database access is secure.

Provide a clear privacy notice, session expiration controls, and a hard-delete action for the owner. Never silently retain live database rows after deletion.
